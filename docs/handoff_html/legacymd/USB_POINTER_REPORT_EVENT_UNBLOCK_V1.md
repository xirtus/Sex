4. gtk + input-linux combo (relative mouse): NO reports — same absolute-vs-relative mismatch

**QEMU XHCI trace evidence (gtk + input-linux combo test):**
```
usb_xhci_fetch_trb addr 0x1f918000, TR_NORMAL  ← sexusb armed interrupt IN TRB
usb_xhci_queue_event v 0, idx 12, ER_TRANSFER, CC_SHORT_PACKET  ← controller completed it!
```

The controller DID process the interrupt IN TRB and queued a Transfer Event at event
ring index 12 with CC_SHORT_PACKET (6 bytes of data). However, sexusb's poll loop
did not consume this event — all 36 poll iterations timed out at phase=RING.

This suggests an event ring index alignment issue: sexusb's ev_idx may not correctly
point to the transfer event after the init phase completes. The init phase consumes
events at indices 0-11, advancing ev_idx to 12. But a PORT_STATUS_CHANGE event at
index 0 (not consumed, not a CMD_COMPLETION) may cause ev_idx misalignment.

I) NEXT REQUIRED AUTOPILOT

**USB_HID_POINTER_PRODUCER_V1_RERUN** — rerun the AP14 proof with real USB reports:

1. **Fix event ring alignment**: Investigate why sexusb's ev_idx doesn't correctly
   point to the interrupt IN Transfer Event at idx 12 after init. The PORT_STATUS_CHANGE
   event at idx 0 during NOOP poll may be breaking the ev_idx advancement:
   - NOOP poll reads idx 0, finds PORT_STATUS_CHANGE (not CMD_COMPLETION)
   - `break` exits poll loop WITHOUT advancing ev_idx
   - Enable Slot poll reads idx 0 again, finds PORT_STATUS_CHANGE (still not CMD_COMPLETION)
   - `break` exits WITHOUT advancing — ev_idx stuck at 0
   - All subsequent events are consumed from wrong indices
   
   Fix: In the NOOP poll, if the event is not CMD_COMPLETION, clear it and advance
   ev_idx before breaking. Or add a dedicated PORT_STATUS_CHANGE handler.

2. **Use absolute input device** for evdev mode: The USB tablet requires absolute
   events. Use `/dev/input/event4` (touchpad) or `/dev/input/eventX` for a drawing
   tablet instead of the relative mouse at `/dev/input/event3`.

3. **Run with gtk mode and operator interaction**: This is the simplest path to
   getting real USB reports — open the GTK window, click inside, move mouse.

4. **After unblock**: All AP14 `usb_pointer_producer_*` gates should transition
   from SKIP to PASS when real USB reports arrive.
